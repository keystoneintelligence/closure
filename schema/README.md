# Closure 0.1 contracts

These JSON Schema 2020-12 documents are generated by `closure schema --output schema` from the same Pydantic models used by the compiler and runtime. Do not edit generated JSON by hand.

| Schema | Boundary |
| --- | --- |
| `project.schema.json` | Project manifest, contexts, policy and scope |
| `module.schema.json` | Authored parameters, interfaces, analyses and requirements |
| `study.schema.json` | Authored study points or parameter grid |
| `runner-request.schema.json` | The engine's JSON stdin request to an analysis |
| `runner-response.schema.json` | The analysis's JSON stdout response |
| `evidence.schema.json` | A sealed successful analysis record |
| `report.schema.json` | A current plan or saved build assessment and model snapshot |
| `study-result.schema.json` | Every result and aggregate coverage for a study |
| `review.schema.json` | A reviewer decision bound to context and assessment identity |

The protocol is language-neutral. A runner can be any authorized executable that reads and writes the documented JSON exchange. It does not need to import Closure or use Python.

Runtime validation rejects unknown fields, coercion of strings or booleans into numeric results, incompatible artifact envelopes, malformed content identities, and nonnumeric solver residuals. Normalized values carry explicit types; runner outputs may omit a type when their authored port supplies it. Quantity outputs must carry a unit. Artifact qualifiers are checked against the port and retained with input and output evidence.

JSON Schema validates document shape. The compiler additionally checks relationships that need the project: symbol resolution, unit compatibility, enum membership, semantic qualifiers, invocation identity, output names, graph cycles, scope, acceptance policy and hash integrity. A structurally valid response alone does not establish a passing engineering requirement. A successful schema check of a report also does not independently re-run its analyses or verify its physical claims.

A plan has no `report_hash`; a saved build has a digest over its body. Evidence records require `record_hash`. Readers validate the original object without inserting schema defaults or changing historical bytes. Optional fields preserve earlier 0.1 records, including evidence created before input-file archiving and reports created before explicit verification-branch diagnostics.

## Canonical identities

The 0.1 protocol uses the reference canonicalization in `closure.io.canonical`: JSON encoded as UTF-8, string object keys sorted by Unicode code point, no insignificant spaces, literal Unicode rather than ASCII escapes, and no NaN or infinity. Numeric serialization follows Python's JSON encoder, preserving distinctions such as integer `1`, float `1.0` and float `-0.0`. This is not a claim of RFC 8785 canonicalization. Non-Python clients can consume recorded digests directly; a client that recomputes them must reproduce these rules and verify against the conformance fixtures.

SHA256 is applied to those canonical bytes. A record's digest excludes its `record_hash`; a report's excludes its `report_hash`. Digests detect changed bytes and support caching, but do not authenticate a reviewer or substitute for repository access control.

The tests in `tests/test_protocol.py` validate real requests, evidence, plans, builds and studies with an independent JSON Schema implementation, reject malformed exchanges, check sealed-history validation, and ensure published schemas match the compiler models.
